## プロセス

![アーキテクチャ](../img/architecture.svg)

1 つの実行ファイルがすべての役割を持ちます：

| 役割 | 起動するもの | 状態 | 備考 |
|---|---|---|---|
| **デーモン**（`--daemon`） | 最初のプロキシ呼び出しまたは CLI 呼び出し、あるいはユーザー。 | すべての状態。 | ランタイムディレクトリごとに 1 つのデーモンが実行されます。ファイルロックがこれを保証します。デーモンは停止するまで実行されます。 |
| **Stdio プロキシ**（引数なし） | MCP クライアント。 | 状態なし。 | プロキシは各ツール呼び出しをデーモンに送ります。必要に応じて、デーモンを起動します。 |
| **CLI**（`tools`、`call`） | ユーザー。 | 状態なし。 | `tools` はデーモンに接続しません。`call` はデーモン経由で 1 回の呼び出しを行います。 |
| **Ghidra**（`analyzeHeadless`） | デーモン。開いているセッションごとに 1 つ。 | 解析結果。 | Ghidra はブリッジをポストスクリプトとして実行します。 |

クライアントは**ローカルソケット**でデーモンに接続します。
Unix では、ローカルソケットは Unix ドメインソケットです。Windows では、名前付きパイプです。
デーモンは、ソケットのアドレスをランタイムディレクトリの `server.json` に書き込みます。
応答するデーモンがない場合、クライアントがデーモンを起動します。
クライアントは新しいデーモンを切り離されたプロセスとして起動します。そのため、クライアントが停止した後もデーモンは実行を続けます。

**ブリッジ**は、`bridge/` サブモジュールにある Java プログラムです。
`cargo xtask build` コマンドは Gradle でブリッジをビルドします。
次に、ブリッジ JAR と起動スクリプト `Bridge.java` を実行ファイルに埋め込みます。
各起動の前に、デーモンはこの 2 つのファイルをランタイムディレクトリに書き込みます。
そして、それらを `analyzeHeadless -postScript` に渡します。
その後、ブリッジは WebSocket でデーモンに接続し、解析 API を提供します。

## ソースのレイアウト

すべての Rust アプリケーションコードは [`src/`](../../src) にあります。
モジュールは、自分より下のレイヤーにあるモジュールだけを使用します：

![ソースコードレイアウト](../img/source_layout.svg)

| モジュール | 責務 |
|---|---|
| `cli` | コマンドライン引数と 3 つの実行モード。 |
| `daemon` | リスナー、ファイルロック、`server.json`、切り離された起動、プロキシ接続再利用、シャットダウン。 |
| `mcp` | MCP ハンドラー。デーモン内で呼び出しを実行するか、プロキシからデーモンに呼び出しを送ります。 |
| `mcp_http` | Streamable HTTP、旧式 SSE セッション、CORS、HTTP 互換性。 |
| `upload` | アップロード資格情報と `POST /upload` エンドポイント。 |
| `tools` | MCP ツール：ドメインカタログ、ローカル操作、呼び出しの検証、`ghidra_help`。 |
| `session` | セッションのオープン、起動、待機、再起動、呼び出し、クローズ。 |
| `analysis` | バックグラウンドジョブとしての自動解析。 |
| `project` | 保存済みのバイナリと Ghidra プロジェクトの準備。 |
| `bridge` | ブリッジ契約、埋め込まれたランタイム、WebSocket、単一のリクエスト。 |
| `jsonrpc` | ブリッジ WebSocket の厳格な JSON-RPC 2.0 コーデック。 |
| `state` | 共有状態：セッションごとに 1 つのエントリと、ジョブ。 |
| `model` | セッション、ジョブ、応答のレコードと、セッションの状態機械。 |
| `error` | 型付けされたドメインエラー（`DomainError`）と JSON-RPC プロトコルエラーコード。 |
| `config`、`paths` | `config.toml`、永続ホーム、ランタイムディレクトリ。 |
| `process` | 子プロセス、ログローテーション（`RollingLogWriter`）、トークン秘匿化、プロセスツリー全体の停止。 |
| `ghidra`、`java_path` | `analyzeHeadless` の検索と、Java 用のパス変換。 |

各モジュールと項目の API ドキュメント（英語）を読むには、`cargo doc --document-private-items --open` を使用します。

## リクエストの流れ

### ツール呼び出し

![ツール呼び出しの流れ](../img/tool_call.svg)

デーモンは `ghidra_help` と、ドメインごとに 1 つの MCP ツール（例：`ghidra_function`）を提供します。
ブリッジのドメインツールは、ブリッジ MCP サーバーのドメイン名と操作名を使用します。
デーモンにはローカル操作もありますが、ブリッジの shutdown 操作は公開しません。
呼び出しには `operation` とその `params` が含まれます。1 つのセッションを指定する操作には、そのセッションの `md5` も含まれます。`md5` は `params` に入れません。
`ghidra_help` は、各操作の `params` スキーマ、md5 ルール（`required`、`optional`、`absent`）、効果を表示します。
ドメインツールの説明は、操作を初めて呼び出す前にスキーマを取得するようクライアントに指示します。
このドキュメントでは、操作をツール名と操作名で表します（例：`ghidra_session open`）。

`tools::call` はカタログ（`tools/catalog.rs`）でドメインと操作を探します。
`params` のトップレベルの必須フィールドを確認し、スキーマが許可しない追加のトップレベルフィールドを拒否します。
その他のパラメータは、ローカルハンドラーとブリッジが確認します。
次に、以下のいずれかを行います：

- `LOCAL_OPERATIONS`（`tools/local.rs`）の**ローカル操作**を実行します：セッション、ジョブ、アップロード、解析の開始。
- ブリッジ契約 `bridge/docs/asyncapi.yaml` の**ブリッジメソッド**をブリッジに送ります。

結果に `structuredContent` がある場合、`content` のテキストブロックに同じ JSON データを含めます。
`content` だけを読むクライアントも結果を使用できます。

ブリッジがエラーを返すと、ツール呼び出しは失敗します。失敗した結果にも構造化された応答が含まれます。
MCP ハンドラーはエラーを型付けされた `DomainError` と JSON-RPC エラーコード（`-32602`、`-32001`、`-32002`、`-32000`、`-32603`）にマッピングします。
ブリッジはデータベーストランザクション障害（HTTP 500 `transaction_failed`）とクライアント引数エラー（HTTP 400 `invalid_request`）を厳密に区別します。

### バイナリを開く

`ghidra_session open` は、デーモンホスト上の `path`、またはデーモンが以前に保存したバイナリの `md5` を受け付けます。
パスの場合、デーモンは MD5 を計算し、ファイルを永続ホームにコピーします。
その後の呼び出しには MD5 だけが必要です。
デーモンは、接続済みのセッションを再利用するか、進行中の起動に参加するか、新しい起動を開始します。
起動については[セッションのライフサイクル](#セッションのライフサイクル)で説明します。
`ghidra_session open` は起動ジョブをすぐに返します。クライアントが `wait` を設定した場合は、ジョブを待ちます。

### バイナリのアップロード

![アップロードの流れ](../img/remote_upload.svg)

クライアントは資格情報を 1 回だけ使用できます。
リクエストは、デーモンが最初のバイトを読む前に資格情報を使用します。
クライアントは、`ghidra_upload prepare` から 10 分以内にアップロードを開始する必要があります。
デーモンは、アクティブなアップロードを停止しません。

### シャットダウン

次のイベントでデーモンは停止します：Ctrl-C、`SIGTERM`、`SIGHUP`、および対応する Windows コンソールイベント。
その後、デーモンは次の手順を実行します：

1. 新しい作業を拒否します。
2. リスナーを停止します。
3. [プロセスの所有](#プロセスの所有)で説明するとおりに、すべての Ghidra プロセスを停止します。
4. すべてのブリッジ接続を閉じます。
5. サーバーが完了するための短い時間を与えます。

セッションはランタイムのスナップショットを保持します。次の起動後、セッションは `stale` になります。

## セッションのライフサイクル

バイナリの MD5 がセッションを識別します。
セッションは次のいずれかの状態を持ちます（`model::SessionStatus`）：

![セッションのライフサイクル](../img/session_lifecycle.svg)

各状態遷移は、`SessionRecord` の `mark_*` メソッドです。
そのため、各遷移の規則は 1 か所にまとまっています。

起動には 4 つの手順があります：

1. **`begin_launch`** はプロジェクトを準備し、以前のプロセスを停止します。
   新しい 256 ビットのブリッジ資格情報を持つ `launching` レコードを保存します。
   また、起動ジョブを作成します。この時点から、そのジョブがセッションを所有します。
2. **`launch_process`** は、ブリッジをポストスクリプトとして `analyzeHeadless` を起動します。
   セッションを `starting` にします。
3. ブリッジが接続し、`ghidra.ready` を送ります。
   **`bridge::handshake`** は資格情報を確認し、接続を割り当てます。
   セッションを `ready` にします。
4. **`wait_ready`** は `ready` を確認し、起動ジョブを完了します。
   プロセスが早く停止した場合、セッションが失敗した場合、または起動に時間がかかりすぎた場合、ジョブは失敗します。

各手順は、最初に自分の起動ジョブまたは資格情報がまだセッションを所有していることを確認します。
新しい起動が以前の起動を置き換えることがあり、クライアントがセッションを閉じることもあります。
このような場合、古い手順は停止し、新しい状態を変更しません。

`disconnected` または `stale` のセッションに対する次のツール呼び出しは、そのセッションを再起動します。
クライアントはこの再起動を意識しません。

## 並行性

デーモンはマルチスレッドの Tokio プログラムです。
`state.rs` の 3 つの仕組みが状態を正しく保ちます：

- **ライフサイクルロック**（`McpState::lifecycle_lock`、非同期）は、セッションのライフサイクル遷移を順番に実行させます。
  遷移は、オープン、起動、ハンドシェイク、切断、クローズです。
  タスクは await をまたいでこのロックを保持できます。たとえば、プロセスの停止中です。
- **状態のミューテックス**は、セッションのマップとジョブのマップを保護します。
  タスクはブロックしない短い区間だけミューテックスを保持し、await をまたいで保持することはありません。
  そのため、ほとんどの状態メソッドは同期的です。
- **ノーティファイア**（`McpState::notify`）は、変更のたびにすべての待機者を起こします。
  各待機者は条件を再確認します。そのため、不要な起床は害になりません。
  起動の待機は、停止したプロセスを見つけるために、毎秒プロセスも確認します。

各セッションは、同時に最大 1 つのブリッジリクエストを持ちます。
同時に送った 2 つ目のリクエストは `session already has a request in flight` で失敗します。
リクエストに応答できるのは、そのリクエストを送った接続だけです。デーモンは、置き換えられたブリッジからの応答を無視します。
ブリッジが切断すると、その未完了のリクエストは `BRIDGE_DISCONNECTED` エラーを受け取ります。

## プロセスの所有

`analyzeHeadless` は JVM を起動するスクリプトです。
そのため、デーモンは 1 つのプロセスではなく、プロセスツリー全体を停止します（`process.rs`）：

- **Unix。** 子プロセスは新しいプロセスグループのリーダーです。
  デーモンは、このプロセスグループに停止のシグナルを送ります。
  デーモンが停止すると、カーネルがその接続を閉じます。`SIGKILL` の後も同じです。
  ブリッジは閉じた接続を検出します。
  接続の切断を検出しない場合、デーモンへのキープアライブ ping が失敗します。
  ブリッジは 5 秒ごとにこの ping を送信します。

  次に、アクティブな分析をキャンセルし、プログラムを保存します。
  Ghidra は終了します。
  デーモンは `exit_deadline_sec=120` でブリッジを起動します。セッションの終了後 2 分以内に Ghidra が終了しない場合、ブリッジは JVM を強制停止します。ただし、保存中は強制停止しません。
  デーモンを監視する別のプロセスはありません。
- **Windows。** デーモンは子プロセスを一時停止状態で起動します。
  プロセスをジョブオブジェクトに入れます。
  次に、プロセスを再開します。
  ジョブオブジェクトは、最後のハンドルが閉じるとすべてのプロセスを強制終了します。このハンドルを持つのはデーモンだけです。

セッションを停止するために、デーモンは次の手順を実行します：

1. プロセスが自分で停止するのを待ちます。待つのは、ブリッジの切断または通常のクローズの後だけです。
2. プロセスツリーに終了を指示します。
3. プロセスツリーを強制終了します。

`config.toml` の `[timeouts]` が、各手順の制限時間を設定します。

子プロセスログは `RollingLogWriter` によって管理されます：
- アクティブなログファイル（`stdout.log`, `stderr.log`, `daemon.log`）は 10 MiB に制限されます。
- 長すぎるログ行は切り詰めます。転送処理は 10 MiB を超える行を `[TRUNCATED_LOG_LINE]` に置き換えます。
- ログが 10 MiB に達するとローテーションし、最大 3 世代のバックアップ（`.1`, `.2`, `.3`）を保持します。
- 機密の Bearer 認証トークンは行境界で `[REDACTED_TOKEN]` に秘匿化置換されます。
- Windows では、デーモンはログファイルの名前を変更する前にアクティブなファイルハンドルを閉じます。
- `daemon.log` が 10 MiB を超える場合、デーモンは開く前にローテーションします。

## ディスク上のファイル

| 場所 | 内容 | 寿命 |
|---|---|---|
| **永続ホーム**（`GHIDRA_MCP_HOME`、デフォルトは `~/.ghidra-mcp` または `%LOCALAPPDATA%\ghidra-mcp`） | `config.toml`、および `binary`、`binary.json`、`binary.lock`、`ghidra/` の Ghidra プロジェクト、`recovery-backups/` のクラッシュ復旧バックアップを含む `projects/<md5>/`。 | 保持されます。 |
| **ランタイムディレクトリ**（システムのランタイムディレクトリまたは一時ディレクトリにある `ghidra-mcp-<uid>`、または `%LOCALAPPDATA%\ghidra-mcp\run`） | `daemon.lock`、`daemon.log`、`daemon.sock`（Unix）、`server.json`、`sessions/<md5>/session.json`、`logs/<md5>/`、`tmp/`、ブリッジファイル、および Unix では `projects` リンク。 | 削除できます。 |

公開処理は、公開先のディレクトリにファイルを一時保存します。
ファイルを同期し、アトミックに名前を変更します。
Unix ではディレクトリエントリも同期します。
Windows では公開ファイルの write-through 移動を要求します。
`binary.lock` の排他ロックはバイナリの検証と公開、および完了マーカー `binary.json` の公開を保護します。
読み取りは同じファイルの共有ロックを取得し、公開完了まで待機します。
書き込み失敗時は自身の一時ファイルだけを削除します。
再度インポートすると、メタデータがない公開済みバイナリを完成できます。

デーモンは認識できない空でない Ghidra プロジェクトを保持し、オープン処理を停止します。
デーモンは、保存済みプロジェクトに `-process` を指定せず `OpenSavedProject.java` を使用します。
そのため、スクリプトが最初のプログラムオープンを制御し、クラッシュ復旧を有効にします。
復旧スナップショットがあれば、先に `.gpr` と `.rep` を一意の `recovery-backups/` サブディレクトリにコピーします。
スクリプトはコピーを同期して公開した後、プログラムを開きます。
バックアップ失敗時はオープン処理を停止します。
スクリプトはブリッジを起動する前に復旧した変更を保存します。
復旧成功後もバックアップを保持します。
デーモンは `.pending-` 接頭辞が付くバックアップを使用しません。

Ghidra は、隠しセグメントを含むプロジェクトパスを受け付けません。しかし、デフォルトのホームは隠しディレクトリです。
そのため、Unix ではデーモンが Ghidra に**プロジェクト起動エイリアス** `<runtime>/projects` を渡します。
このエイリアスは、永続ホームの `projects/` ディレクトリへのシンボリックリンクです。

## インターフェース

| インターフェース | 形式 | 契約 |
|---|---|---|
| MCP ツール `ghidra_*` | stdio、ローカルソケット、Streamable HTTP、または旧式 SSE による MCP。 | `LOCAL_OPERATIONS` とブリッジ契約にある操作。`ghidra_help` がそれらを説明します。 |
| ブリッジ WebSocket `/ws/agent` | 厳格な JSON-RPC 2.0（`jsonrpc.rs`）。 | ブリッジのビルドが生成する `bridge/docs/asyncapi.yaml`。 |
| アップロード `POST /upload` | bearer 資格情報付きの生のバイト列。 | `ghidra_upload prepare` の結果。 |
| `server.json` | `pid`、`mcpUrl`、`bridgeWsUrl`、`localSocket` を含む JSON。 | ローカルクライアントが読み取ります。 |
| `config.toml` | TOML。 | README と `config.rs`。 |
| エラーエンベロープ | MCP `structured_content` 内の JSON。 | 標準 JSON-RPC エラーコード（`-32602` から `-32603`）および機械可読なエラーバリアント。 |

MCP ツールの定義、操作のスキーマ、ヘルプの出力、応答の形式は公開の契約です。
これらは意図的な変更でだけ変更してください。
その変更を変更履歴に記録してください。

## セキュリティモデル

デーモンは、ローカルユーザーと、ユーザーが実行する解析ツールにサービスを提供します。
他のホストからデーモンにアクセスできるようにしないでください。

- **リスナー。** デーモンはループバックアドレスだけを受け付けます。
  `/mcp` または `/upload` へのリクエストは、リスナーの Host を持つ必要があります。
  `/mcp` は有効な HTTP または HTTPS Origin を受け付け、CORS ヘッダーを返します。
  `/upload` はリスナーの Origin だけを受け付けます。
- **ローカルソケット。** Unix では、ソケットは非公開のランタイムディレクトリにあります。
  Windows では、ランダムな名前の名前付きパイプです。そのアクセスリストは所有者だけに接続を許可し、リモートクライアントを拒否します。
- **ランタイムディレクトリ。** 起動のたびに、デーモンはこのディレクトリが実際のディレクトリであることを確認します。
  現在のユーザーが所有し、モードが `0700` である必要があります。
  そのため、他のユーザーはその中のファイルを読むことも、ファイルを置くこともできません。
- **ブリッジ資格情報。** 資格情報はランダムな 256 ビットのトークンです。
  デーモンはこれを `Authorization` ヘッダーでだけ送り、ディスクには書き込みません。
  デーモンは Ghidra のログからこれを取り除きます。
  セッションが閉じるか、デーモンが再起動すると、資格情報は無効になります。
- **アップロード資格情報。** クライアントは資格情報を 1 回だけ、1 つの MD5、1 つのファイル名、1 つのサイズに対して使用できます。
  デーモンは、バイト列を保存する前に確認します。
  デーモンはアップロードを拒否した後、残りのバイト列を読み取って破棄します。上限は 1 GiB と 30 秒です。
  そのため、本文をすべて送信してから応答を読み取るクライアントも、エラーを受け取れます。
- **クライアントへのメッセージ。** エラーメッセージと要約には、絶対パスも資格情報も含まれません。

脆弱性の報告方法は [SECURITY.md](../../SECURITY.md)（英語）が説明します。

## システムの拡張

- **ローカル操作。** `src/tools/local.rs` の `LOCAL_OPERATIONS` にエントリを 1 つ追加します。
  ドメイン、名前、説明、パラメータスキーマ、md5 ルール、効果、ハンドラーを指定します。
  ブリッジメソッドにライフサイクルの動作を追加する場合は、`extends` にそのメソッドを設定します。
  `parse` を使用して、パラメータを `Deserialize` 構造体に読み込みます。
  これで `ghidra_help`、ツール定義、検証にその操作が含まれます。
- **ブリッジメソッド。** ブリッジにメソッドを追加します。
  メソッドを追加した後、契約を再生成します。
  デーモンはコンパイル時に契約を読み込み、そのメソッドをドメインツールで提供します。
  新しいドメインの場合は、`src/tools/catalog.rs` の `DOMAINS` にドメインを追加します。
  ブリッジの MCP サーバーがメソッドを別のドメインに割り当てる場合は、`bridge_target` に同じドメイン名と操作名を追加します。
- **セッションの状態または遷移。** `model.rs` の `SessionRecord` に `mark_*` メソッドを追加します。
  ライフサイクルロックを保持しているときに呼び出します。
- **長時間の処理。** `McpState::insert_job` でジョブを作成します。
  タスクで処理を行います。
  `McpState::finish_job` でジョブを完了します。
  `McpState::await_job` の結果を返します。
  これで、呼び出し側が待つかどうかを選べます。
- **設定値。** `config.rs` の該当するセクションにフィールドを追加します。
  デフォルト値とドキュメントコメントを付けます。
  README に記載します。
